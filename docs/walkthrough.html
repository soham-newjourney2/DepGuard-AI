DepGuard AI · project walkthrough · 20 Oct 2026

From a lockfile to a proven fix.

DepGuard AI takes a project (a zip, a GitHub link or a live website), finds every dependency with a known advisory, shows the exact path from your code to it, ranks it with cited evidence, proposes the smallest defensible fix and, for npm, proves that fix in a locked-down container. This page walks through every step, the security model, the code map, and what to build next.

What goes in

Four ways to start a scan

Zip upload

A project folder with its lockfile. Checked for size, file count, compression ratio and hostile paths before anything is extracted.

GitHub link

github.com/o/r, /tree/<branch>/<folder>, /blob/…, .git, git@… or owner/repo@ref. Downloaded from codeload only.

Website URL

One public page is read as text. Libraries are recognised from <script> URLs and license banners. No JavaScript runs.

Bundled demos

vuln-demo (22 findings), messy-demo (73), python-demo (38), site-demo (65). All work offline from recorded OSV data.

Every arrow above is a real module in backend/app/. The API process never runs npm, node or anything from an upload. Only the disposable worker container does.

Step by step

What happens to your project, in order

  1. 01

    Intake: make the archive safe to look at

    intake.py · routes/jobs.py · github.py · stacks/__init__.py
    • Limits: MAX_UPLOAD_MB 15, 5,000 files, 80 MB unzipped, compression ratio ≤ 100 (zip-bomb defence). Declared sizes are re-checked while streaming.
    • Rejects absolute paths, .., drive letters, alternate data streams, reserved device names and symlinks. Skips node_modules, .git and nested archives.
    • Project discovery walks up to four folders deep, skipping vendor, virtualenvs and build output. One lockfile-backed project is chosen automatically. Several projects (for example web and api#Python) produce a picker.
    • A manifest without a lockfile gets a precise hint, such as poetry lock, pip freeze > requirements.txt or cargo generate-lockfile.
    • GitHub links: /tree/feature/x/server is ambiguous, so DepGuard tries ref feature, then feature/x (at most four splits) against codeload. The rest of the path becomes the project folder.
  2. 02

    Parse: one dependency graph for every stack

    lockfile.py · graph.py · stacks/{python,go,rust,php,ruby,dotnet,java}.py
    • npm: package-lock.json v2/v3 resolved the way Node resolves nested node_modules, including links, aliases and peer/optional flags.
    • Python: uv.lock, poetry.lock, Pipfile.lock and pinned requirements*.txt. pip-compile's # via comments become real edges.
    • Go go.mod (direct vs // indirect, replace), Rust Cargo.lock, PHP composer.lock, Ruby Gemfile.lock with Gemfile groups, .NET packages.lock.json, Java gradle.lockfile.
    • Each package gets a scope (prod/optional/peer/dev), a depth and every path from the root (shortest first, capped at 20). Lockfiles that do not record edges raise W_FLAT_LOCK instead of inventing paths. Unpinned requirements raise W_UNPINNED and are never guessed.
  3. 03

    Scan: ask OSV about every installed version

    scanner/osv_api.py · osv_cli.py · fixture.py · cache.py · versions.py
    • Batch query to OSV with the right ecosystem (npm, PyPI, Go, crates.io, Packagist, RubyGems, NuGet, Maven), then hydrated advisories, cached for 24 h.
    • Version ordering is per ecosystem: PEP 440 for Python, semver for npm/Go/Rust/PHP/.NET, and tokenised ordering for Ruby and Maven (1.2.3.beta < 1.2.3).
    • If OSV is down during a bundled demo, the recorded scan is used and labelled “Cached scan from … — live scanner unavailable.”
  4. 04

    Normalise: one finding per advisory and package

    scanner/normalize.py
    • GHSA ids are preferred and CVE aliases merged. CVSS v3/v4 vectors are scored, and the installed version is matched against affected ranges (SEMVER, ECOSYSTEM and explicit version lists). Fixed versions are taken only from the advisory.
  5. 05

    Reachability: is it imported?

    reachability.py · web/site.py
    • Literal imports are indexed per language: JS/TS require/import, Python import/from (with distribution→module aliases such as PyYAML → yaml), Go import paths, Rust use, Ruby require.
    • Labels: Strong evidence (the package itself is imported), Possible (a parent is imported), Not observed, Unknown (dynamic imports, or a language without analysis). Test files are counted separately.
    • For websites the evidence is the exact <script> line that loads the library.
  6. 06

    Prioritise: a transparent score with citations

    prioritize.py · evidence.py · policy.py
    • Signals: severity, scope, fix availability, depth, reachability and exposure. Each one cites a numbered evidence item (E1 advisory, E2 path, E3 scope, E4 fix, E5 reachability, E6 scan).
    • Bands P1–P4, with flags such as “no fix” or “depth unknown”. An optional depguard.policy.json turns this into a pass/fail verdict.
  7. 07

    Explain: Claude, but only from evidence

    ai/context.py · anthropic_provider.py · grounding.py · template_provider.py
    • Claude receives a redacted context of at most 6 KB: the finding, its evidence and the fix candidates. It never receives your source code.
    • The reply must match a JSON schema. A grounding validator strips any version, advisory id or citation that is not in the evidence. Without an API key, a deterministic template writes the explanation.
  8. 08

    Fix: the smallest change that clears the advisory

    remediation/candidates.py · batch.py · generic.py · patch.py
    • npm: uses real registry metadata to try a direct bump, a parent bump (simulated), a nested overrides entry, or reports “no safe upgrade”. Results are ranked by least change and re-checked against OSV. Diffs keep your package.json indentation, line endings and BOM.
    • Other stacks: the smallest fixed version that clears every advisory on the package, plus the package-manager command (pip install, go get, cargo update --precise, composer require, …). The diff is real where the pin is plain text: requirements.txt, go.mod, or a page's <script src>.
    • Plan all fixes merges every finding into one change and reports conflicts instead of hiding them.
  9. 09

    Verify (npm): prove it in a disposable container

    verify/runner.py · verify/modes.py · worker/Dockerfile · worker/entry.sh
    • Nothing runs until you approve. The dialog lists exactly what will run. The edit is applied to a copy, then: resolve → test (no network) → OSV rescan → before/after comparison.
    • Other stacks and websites are clearly marked “not verified”, and the Approve button is not offered for them.
  10. 10

    Report: resolved, still present, new, unverifiable

    report/compare.py · export.py · sbom.py
    • The VERIFIED seal appears only when the target advisory is gone and tests ran and passed. Test results are kept separate from the scan result.
    • Exports: JSON, Markdown, self-contained HTML (with its own CSP), .patch, and a CycloneDX 1.5 SBOM with the right purl for every ecosystem (pkg:pypi/…, pkg:golang/…, …).
Worked example · vuln-demo

One finding, end to end

root→express@4.17.1→body-parser@1.19.0→qs@6.7.0

qs@6.7.0 matches GHSA-hrpp-h998-j3pp (high, prototype pollution), fixed in 6.7.3. It is transitive and in production scope, reached through two paths. index.js:1 imports express, so reachability is “Possible”.

  • E1Advisory, severity and affected range, taken from OSV.
  • E2Path: depth 2, 2 paths from the root, read from package-lock.json.
  • E3Scope prod: it ships with the application.
  • E4Fixed in 6.7.3, according to the advisory.
  • E5express, which pulls in qs, is imported at index.js:1.
  • E6Scanner, version and timestamp.

The fix is a parent bump of express, so the newer body-parser pulls a fixed qs. After approval, the container resolves, runs npm test with no network, and rescans. The report shows the advisory as Resolved and 22 findings drop to 9.

Security model

Why it is safe to point at untrusted code

The API never executes uploads

  • Lockfiles are parsed as data with Python's own TOML and JSON parsers.
  • No package manager is called by the API. Only the worker image runs npm.
  • Untrusted text is never placed in innerHTML. The UI builds DOM nodes with dom.h() under a strict same-origin CSP.

Live sites without SSRF

  • http(s) on ports 80/443 only, and every resolved IP must be public. Loopback, private, link-local (including 169.254.169.254), CGNAT, and mapped/6to4/Teredo forms are blocked.
  • The connection is pinned to the vetted IP, using the Host header and SNI. DNS rebinding cannot swap the target.
  • At most 5 redirects, each re-checked. Byte caps, no cookies, no proxies, no JavaScript.

AI is grounded and redacted

  • Tokens, keys, JWTs and URL credentials are redacted before anything is logged or sent.
  • Evidence is passed as data, never as instructions. Anything the model invents is stripped.

Recommendation

Next feature: verify fixes for every stack

DepGuard's promise is “proves it in an isolated container”, but today that proof exists only for npm. A Python, Go or Rust user gets a correct command and diff, labelled “not verified”. That is honest, but it is also the largest gap between what the product claims and what it delivers. Closing it makes every new stack from P12 a first-class citizen.

Why this, why now

  • Trust: the VERIFIED seal is the product's signature moment. Today 7 of 8 lockfile stacks can never earn it.
  • Reuse: the runner, stage model, log redaction, rescan and comparison are already stack-agnostic. Only the commands and images are npm-specific.
  • Safety needs it: some ecosystems execute code while resolving (Python build backends, Rust build.rs, Ruby native extensions). That can only happen in the sandbox, never in the API.

What to change

  • verify/recipes.py (new): one Recipe per stack with image, resolve command, test command, lockfile, and whether resolve needs network.
  • worker/: add python:3.12-slim, golang:1.23 and rust:1.82-slim images pinned by digest. entry.sh takes a recipe id, never a command.
  • remediation/generic.py: emit real edits (file + old/new text), not only a diff, so the runner can apply them to the workspace copy.
  • verify/runner.py: pick the recipe from meta.json, rescan the new lockfile with stacks.BY_ID[stack].load(), then reuse compare.
  • routes/verify.py and fix.js: drop E_VERIFY_UNSUPPORTED for stacks that have a recipe, and show that stack's own command list in the approval dialog.

Recipes (first three)

  • pip: pip install --only-binary=:all: -r requirements.txt (no sdist builds, so no setup.py runs), then pytest -q with no network.
  • Go: go mod download && go mod tidy, then go test ./... with GOFLAGS=-mod=mod and no network.
  • Cargo: cargo update -p x --precise v && cargo fetch, then cargo test --offline.

Risks and how to contain them

  • Image size and pull time: build images on first use and cache them. The UI says “preparing Python sandbox”.
  • Code runs during resolve: the same flags as npm (--read-only, --cap-drop ALL, non-root, pids/memory/CPU caps). Network is allowed only during resolve.
  • Projects without tests: the seal stays “partially verified”, as it does for npm today.

Definition of done

  • test_recipes.py: each recipe's exact argv and container flags (no user-controlled strings).
  • Docker-marked tests: the python-demo pyyaml 5.3.1 → 5.4 fix reaches VERIFIED, and a Go fixture golang.org/x/net bump passes go test.
  • e2e: Python demo → Propose a fix → Approve → verification terminal → report seal.
  • SECURITY.md lists every new stage and flag. Effort: about one phase (5–6 tasks).
